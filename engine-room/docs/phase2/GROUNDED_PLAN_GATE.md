# Phase 2: Grounded Understanding & Useful Plans — preregistered gate

**Status:** registered before implementation. Freeze these 12 cases and thresholds before any Phase 2 code changes. Case labels and expected outcomes are the evaluation contract; implementation must not be used to relabel them.

## Product boundary

An operator request must produce either (a) a bounded clarification request when goal or acceptance cannot be resolved, or (b) a reviewable plan grounded in the repository facts that were actually supplied. Intent owns understanding; Planning owns plan construction. The operator surface and spine transport data only. Plans are proposals: this phase does not authorize policy or execution. Replay reconstructs recorded interpretation and plan facts without calling any model.

Reuse `RepositoryProfile` and `GroundingAssembler`/`ContextEngineeringService` as existing fact producers, and `GroundedPlanner`/`PlanningService` as the plan producer. The current seam has a known gap to close: `GroundingInputs` supports `intent` and `repository_profile`, but `ConstitutionalPipeline._stage_context` currently passes neither. `HumanInteraction.submit(..., control=SpineControl(stop_after_stage=SpineStage.PLANNING))` already provides a plan-before-actuation boundary. Do not place semantic decomposition in the CLI or spine; keep interpretation data in Intent and plan construction in Planning.

## Frozen fixture repository

Create a temporary, deterministic Python fixture repository with only these tracked files (UTF-8, LF):

- `pyproject.toml`: project `fixture-cli`, Python `>=3.11`, pytest and Ruff configured.
- `README.md`: states the CLI entry point is `src/fixture_cli/main.py`, commands are `run` and `status`, and tests run with `python -m pytest`.
- `src/fixture_cli/main.py`: argparse CLI with `run` and `status`; no `--version` option.
- `src/fixture_cli/config.py`: `load_config(path)` returns a dict and raises `FileNotFoundError` when absent.
- `src/fixture_cli/export.py`: `export_json(data, path)` writes JSON.
- `tests/test_main.py`: tests `run` and `status`; no version test.
- `tests/test_config.py`: tests successful config load only.
- `tests/test_export.py`: tests JSON output.

The fixture profile is generated by the existing `RepositoryIntelligence` producer from that tree. The provenance bundle records the profile identity, scanner version, root, file inventory, emitted evidence, and the exact source references used by each case. A plan may cite only paths in this fixture inventory. The profile is facts-only; any derived target/rationale must be labeled as an interpretation, not presented as a repository fact.

## Registered cases

Cases are listed before implementation. “References” names the only acceptable file references for that case; generated citations must be a subset of these paths and each must exist in the fixture. Facts such as Python, pytest, CLI entry point, commands, and current missing `--version` support must be supported by the listed file(s) and the recorded profile bundle.

### A — ambiguous requests; clarify before producing a plan (4)

| ID | Operator request | Expected clarification | Acceptable source references |
|---|---|---|---|
| A1 | “Fix the CLI.” | Ask which behavior or defect is wrong and what outcome is expected. No Goal/Plan or inferred file target. | `README.md`, `src/fixture_cli/main.py` |
| A2 | “Make configuration better.” | Ask which configuration behavior and acceptance condition should change. No guessed redesign. | `src/fixture_cli/config.py`, `tests/test_config.py` |
| A3 | “Improve exports.” | Ask what export format/behavior or failure needs improvement. Do not assume JSON is the requested change. | `src/fixture_cli/export.py`, `tests/test_export.py` |
| A4 | “Update the CLI appropriately.” | Ask what “appropriately” means and which user-visible behavior is wanted. No plan until answered. | `README.md`, `src/fixture_cli/main.py` |

For each, preserve the clarification question and its reason in a transcript artifact. After a synthetic operator answer states a concrete outcome and acceptance condition, the next operator submission may resolve and produce a plan; the original unresolved submission must never be retroactively rewritten.

### B — clear, atomic requests; exactly one work item (4)

| ID | Operator request | Expected plan | Acceptable source references |
|---|---|---|---|
| S1 | “Add a `--version` option to the CLI that prints the installed version and exits; add a focused test for the option.” | One atomic package covering the CLI option and its focused test. No invented preliminary steps or dependencies. | `src/fixture_cli/main.py`, `tests/test_main.py`, `pyproject.toml` |
| S2 | “When the config file is missing, return an empty config dict; add a test for that behavior.” | One atomic package covering missing-file behavior and its regression test. | `src/fixture_cli/config.py`, `tests/test_config.py` |
| S3 | “Add a test confirming `export_json` writes valid JSON that can be read back.” | One test-only package. Do not propose implementation changes unsupported by the request. | `src/fixture_cli/export.py`, `tests/test_export.py` |
| S4 | “Document the existing `run` and `status` commands in the README, including the test command.” | One documentation package. Preserve the already documented CLI and test facts. | `README.md` |

Each output must state the requested outcome, acceptance condition, repository facts actually used, explicit assumptions/uncertainty (empty only when none), and source references. Exactly one work item and no dependency edge is the atomic-plan criterion.

### C — genuinely multi-step requests; explicit declared dependencies (4)

| ID | Operator request | Expected work items and dependency edges | Acceptable source references |
|---|---|---|---|
| M1 | “Add a `--version` option to the CLI. Implement it first, then add a test that verifies the printed version and exit behavior.” | `implement-version` → `test-version`; test depends on implementation. | `src/fixture_cli/main.py`, `tests/test_main.py`, `pyproject.toml` |
| M2 | “For missing config files, make `load_config` return an empty dict. First change the function, then add a regression test for the missing-file case.” | `change-missing-config` → `test-missing-config`. | `src/fixture_cli/config.py`, `tests/test_config.py` |
| M3 | “Add CSV export alongside JSON. First implement `export_csv`, then test that the output can be parsed back as rows.” | `implement-csv-export` → `test-csv-export`; no unrequested JSON changes. | `src/fixture_cli/export.py`, `tests/test_export.py`, `pyproject.toml` |
| M4 | “Add a `--version` option and document it. Implement the option first; then write its test and update the README. The test and documentation can happen independently after implementation.” | `implement-version` → `test-version` and `implement-version` → `document-version`; no edge between the latter two. | `src/fixture_cli/main.py`, `tests/test_main.py`, `README.md`, `pyproject.toml` |

The dependency criterion is exact: every declared edge matches the request’s ordering; no missing required edge and no invented edge. The two M4 follow-up items must be parallelizable. Plan output must keep source facts separate from inferred task decomposition and state any uncertainty.

## Evidence bundle and replay check

For every case, persist a machine-readable provenance bundle containing the raw request labeled as operator-provided, fixture tree/profile identity and profile facts, selected and omitted grounding records with reasons, Intent artifact/version, downstream context-package and plan identities when present, work-item keys/objectives, dependency edges, assumption/uncertainty fields, citations, cited fixture-source SHA-256 hashes, and explicit absent-artifact markers. Repository-profile facts and request-derived plan outcomes must be labeled separately; a path inventory establishes path existence, while the fixture hashes establish the exact fixture bytes used by the evaluation. A1–A4 stop at clarification: record that Goal, ContextPackage, and Plan are absent and include no downstream grounding selection. Preserve all four clarification transcripts. Capture a replay trace by reopening the durable event store and reconstructing the Intent and ExecutionPlan from recorded facts while replacing the interpreter/model seam with a spy that raises if invoked. The trace must show zero interpretation/model calls and zero repository rescans during replay.

The final evaluation report records each case as pass/fail, observed output, failures (including false citations, wrong/missing clarification, unsupported repo claims, missing/wrong dependency edges, hidden assumptions, and replay calls), aggregate counts, and the thresholds below. Do not omit failed cases.

## Pass thresholds (all required)

- 12/12 registered cases meet their expected outcome; each category is 4/4.
- 0 fabricated, nonexistent, or case-disallowed repository references across all plans and provenance bundles.
- All 4 ambiguous inputs request clarification before any Goal/Plan; clarification transcripts preserve the question and reason.
- All 4 atomic inputs produce exactly one work item and zero dependency edges.
- All 4 multi-step inputs produce the registered work items and exact dependency edges, including M4’s independent follow-up items.
- 100% of non-empty factual claims about the fixture in plans/provenance are traceable to fixture content or the recorded RepositoryProfile; assumptions and unresolved uncertainty are visible before execution.
- Replay reconstructs recorded understanding and plan with 0 model/interpreter invocations and 0 repository rescans.
- The operator-path end-to-end case stops at `PLANNING`; no actuation or execution occurs before a separate operator action.
